# Fund Trading Demo

A minimal fund trading backend. It covers the core chain: user order → order state machine → downstream submission (mock) → batch confirmation → reconciliation.

Scope: fund purchase and redemption, T+N confirmation, idempotent order intake, downstream timeout handling, and an UNKNOWN-state reconciliation loop.

## Components

- `api` — HTTP intake. Validates input, enforces idempotency keys, writes orders. Does NOT decide final order state.
- `order-core` — order state machine. Single owner of state transitions.
- `downstream-mock` — simulates the fund registrar. Returns success, explicit failure, or timeout. Timeout means UNKNOWN, not failure.
- `job-worker` — batch tasks: submit pending orders, confirm T+N, reconcile UNKNOWN orders.
- `reconciliation` — queries downstream for UNKNOWN orders and forces a terminal state. It is the safety net, not a retry.

Dependency rule: `api` → `order-core` ← `job-worker`/`reconciliation`; `order-core` → `downstream-mock`. No component bypasses `order-core` to touch order state.

## Key Decisions

- **Order states**: `CREATED → SUBMITTED → CONFIRMED / FAILED`, plus `SUBMITTED → UNKNOWN`. A downstream timeout maps to `UNKNOWN`, never to `FAILED`. `UNKNOWN` resolves only through reconciliation (query, never resubmit).
- **Idempotency**: client-supplied `Idempotency-Key` header + unique index on `(user_id, idempotency_key)`. Replay returns the original result with `200`, not `409`.
- **T+N**: cutoff 15:00 Asia/Shanghai; trading-day math lives in one calendar module; `trading_day` and `confirm_date` are stamped at intake.
- **Job model**: at-least-once dispatch + idempotent handlers. Jobs sharded by `order_id` so one order is processed serially. Retry with exponential backoff and a max-attempts cap.
- **Observability**: one request ID from `api` intake, propagated through every log line and downstream call; `GET /debug/trace?request_id=` for on-call.

## Hard Constraints

- NEVER write order state outside `order-core`.
- NEVER treat a downstream timeout as failure.
- NEVER submit a new order from reconciliation; query only.
- NEVER rely on application-level dedup alone; the unique index must exist.
